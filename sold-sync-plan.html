Airtable Sold Sync + Invoice Automation

Move the Val.town automation into the Go service, keep dev/prod Stripe routing through APP_ENV, and use Airtable as the operational source of truth.

LEADS base: appg9012rLh2diVLq Table: tblui0E6mBFkHGWvZ Platform: exe.dev

Goal

One Airtable action becomes the customer setup workflow.

1

Status set to Sold

Airtable automation calls the internal Go endpoint with the record ID.

2

Create CompanyCam project

Use lead contact/address data and upload any Airtable attachment photos into the project.

3

Create Stripe customer

Use the same lead data, then save the returned cus_... ID back to Airtable.

4

Make Invoice when ready

A second Airtable checkbox creates/finalizes a Stripe invoice and saves the hosted invoice link.

Endpoint 1

POST /sold/sync

Triggered when the lead/customer record is marked Sold.

Input

{"recordId":"rec..."}

Auth: Authorization: Bearer $WEBHOOK_AUTH_KEY

CompanyCam

  • Create project from full name + address.
  • Add primary contact from name/email/phone.
  • Download Airtable photos and upload them to the project.
  • Patch CCam ID.

Stripe

  • Create customer in sandbox or live account based on APP_ENV.
  • Patch stripeID.
  • Skip if ID already exists.

Endpoint 2

POST /invoice/create

Triggered when Make Invoice is checked after the Stripe customer exists.

Guardrails

  • Require existing stripeID.
  • If stripeInvoiceLink exists, return success without duplicating.
  • Use bearer auth like other internal endpoints.

Stripe actions

  • Create invoice item using configured Stripe product/price.
  • Send Airtable Feet as the invoice item quantity.
  • Create + finalize invoice.
  • Read hosted_invoice_url.

Airtable result

  • Patch stripeInvoiceLink.
  • Optionally clear Make Invoice.
  • Optionally set/send invoice later.

Duplicate + Failure Protection

Patch IDs immediately and skip existing work.

Safe retries

  • If CCam ID exists, skip CompanyCam.
  • If stripeID exists, skip Stripe customer creation.
  • If invoice link exists, skip invoice creation.

Partial failure handling

  • Patch each external ID as soon as that call succeeds.
  • If photo upload fails, decide whether project creation still counts as success.
  • Email/log errors for manual follow-up.

Known edge case

If CompanyCam creates a project but Airtable patch fails, retry may duplicate the project. We can add search/idempotency later if it becomes a problem.

Build Status

Both endpoints shipped — auth, validation, and idempotency verified.

New files

  • services/sold_sync.go — POST /sold/sync handler. Creates CompanyCam project (primary contact + photo uploads), then Stripe customer. Patches each ID back to Airtable immediately after creation so retries can't duplicate.
  • services/invoice.go — POST /invoice/create handler. Validates stripeID + Feet, short-circuits if stripeInvoiceLink already set, looks up the Stripe product's default_price, creates invoice item with quantity=Feet, creates and finalizes the invoice, patches the hosted URL back to Airtable.

Extended files

  • services/leads.go — added field IDs for phone, full name, address, status, CompanyCam ID, Stripe ID, invoice link, Make/Send Invoice; expanded the Lead struct; added PatchLeadFields() targeting the LEADS base.
  • services/config.go — added InvoiceProductID (env-switched), CompanyCamBaseURL/APIToken/UserEmail, and RequireBearerAuth() which fail-closes when WEBHOOK_AUTH_KEY is empty.
  • server.go — registered /sold/sync and /invoice/create.
  • SERVICES.md — documented both endpoints with field IDs, payload, idempotency notes, and curl examples.

Design highlights

  • Zero new dependencies — direct net/http calls following the existing services/checkout.go pattern.
  • Stripe owns the unit price — env var holds a Product ID, not a Price ID. The handler reads product.default_price at invoice time so the $/linear-foot rate is changed in the Stripe dashboard, not in code.
  • Photo upload is non-fatal — project creation still counts as success if a photo URL fails. Stripe customer creation failure blocks the response (it's the critical path for invoicing).
  • Auth is strict — missing WEBHOOK_AUTH_KEY rejects every request, even with a matching empty token from the client.

Why Not Local

The exe.dev proxies are unreachable from your laptop.

What happens

Both airtable.int.exe.xyz and stripe-test-mode.int.exe.xyz resolve to 169.254.169.254 — the AWS instance metadata IP. Only processes running inside the VM can reach them. From a laptop you get dial tcp 169.254.169.254:443: connect: no route to host.

The fix

Skip local dev. Push to GitHub, pull on the VM, rebuild, restart the systemd service, then curl the endpoints from inside the VM or from the public URL. Stripe and Airtable credentials are already injected by the proxies in that environment.

Deploy + Test on exe.dev

Push, pull, rebuild, restart, curl.

1

Push from your laptop

git add .gitignore .env.example SERVICES.md server.go \
        services/config.go services/leads.go \
        services/invoice.go services/sold_sync.go \
        sold-sync-plan.html
git commit -m "feat: /sold/sync + /invoice/create endpoints"
git push origin main

Sanity check first: git status must NOT list .env.local. The new .gitignore entry takes care of that.

2

Add the new env vars to /etc/tts/secrets.env on the VM

Before restarting, append the variables the new endpoints need. Without these, /invoice/create returns 500 and /sold/sync can't create CompanyCam projects.

sudo nano /etc/tts/secrets.env

# Append:
STRIPE_INVOICE_PRODUCT_ID_DEV=prod_Uc6pEX6LZHcEcL
STRIPE_INVOICE_PRODUCT_ID_PROD=prod_...
WEBHOOK_AUTH_KEY=
COMPANYCAM_BASE_URL=https://api.companycam.com/v2
COMPANYCAM_API_TOKEN=
COMPANYCAM_USER_EMAIL=stetson@tts.lighting
3

Pull, rebuild, restart

cd /path/to/tts-go
git pull origin main
go build -o tts-server .
sudo systemctl daemon-reload   # only needed if you edited the unit
sudo systemctl restart tts.service
journalctl -u tts.service -n 30 --no-pager

Confirm the boot log shows 🟡 STRIPE MODE: SANDBOX (dev) and no warnings about missing env vars.

4

Pick a real LEADS record ID

Open the LEADS base (appg9012rLh2diVLq) in Airtable, find a test lead with address + phone + photo, copy its RecordID formula value (looks like recXXXXXXXXXXXXXX).

5

Test POST /sold/sync

# From the VM (loopback) — or from your laptop hitting the public URL:
WEBHOOK_AUTH_KEY=$(sudo grep ^WEBHOOK_AUTH_KEY /etc/tts/secrets.env | cut -d= -f2-)

curl -X POST https://tistheseasonkc.com/sold/sync \

  -H "Content-Type: application/json" \
